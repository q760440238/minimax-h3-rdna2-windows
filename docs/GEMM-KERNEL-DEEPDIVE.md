# GEMM 底层内核还能优化什么

日期：2026-11-02
全部基于本会话实测（RX 6900 XT / gfx1030，峰值 46.08 TFLOPS）。

---

## 一、先看一条关键曲线：解包复杂度决定上限

同一形状（5376×28672×2835）、同一个 MMQ 内核、同一块卡，**只换量化格式**：

| 格式 | TFLOPS | 占峰值 | 每 32 值需要做什么 |
|---|---:|---:|---|
| **Q4_0**（J=128） | **40.27** | **87%** | 1 个 fp16 scale，4-bit → int8 |
| Q4_1（J=128） | 37.24 | 81% | 1 个 scale + 1 个 min |
| Q8_0 | 32.27 | 70% | 纯 int8，无解包 |
| Q4_K（J=128） | 27.92 | 61% | **8 个子块，各带 6-bit scale + 6-bit min** |
| Q6_K（J=128） | 24.46 | 53% | 16 个子块 + 6-bit 高位重排 |

**结论：这张卡的瓶颈不是 LDS、不是 occupancy、不是 tile 形状——是解包。**

Q4_0 能跑到 87%，说明内存、dp4a 流水、网格调度全都没问题。
Q4_K 掉到 61%，差的 26 个百分点全是「每个 32 元素子块要单独取 scale/min 并应用」的开销。

这也解释了为什么之前所有的 tile 调参（J、I、occupancy、stream-K）最多只有 ±10%：
**它们动的是搬运，而瓶颈在算术。**

---

## 二、q4_K 的解包为什么贵（源码级）

`mmq-load-tiles.cuh` + `mmq-vec-dot.cuh` 里，q4_K 每个 256 值超级块：

1. `K_SCALE_SIZE = 12` 字节里打包了 8 个 6-bit scale 和 8 个 6-bit min
2. 取一个子块的 scale 要：移位 + 掩码 + 合并（两个字节拼 6 bit）+ 转 half
3. 4-bit → int8 展开：每 4 字节两条 `shift` + 两条 `and`
4. 内层 dp4a 之后，**每个子块还要一次 `scale * acc` 和 `acc += min * sum`**

对比 q4_0：只有**一个** fp16 scale，直接 `d * dot(int8)`，没有 min、没有子块。

---

## 三、可以动的四个点（按预期收益排序）

### P1.（已推翻）把 scale 应用搬到外层 —— 寄存器不允许

**先前的假设**：内层每个子块都做 `scale*dot + min*sum`，把它搬到外层能省浮点运算。

**读了实现之后发现这个假设是错的**（`mmq-vec-dot.cuh` + `mmq.cuh`）：

```cpp
float sum[J*I / (nwarps*warp_size)] = {0.0f};   // J=I=128 时 = 64 个 float/线程
```

- 累加器已经是 **64 个 float 每线程**（J=128, I=128, nwarps=8, warp_size=32）。
- scale 已经是「每个子块算完立刻应用」，**不存在重复计算**。
- 改成「8 个子块各一个累加器」需要 512 个 float/线程；occupancy 2 时每线程寄存器上限约 128。
  **物理上不可能。**

所以 P1 这条路是死的。真正的开销构成要重新分析（见下）。

### P1'. 再纠正一次：6-bit scale 其实**已经**在加载阶段预解包了

读 `mmq-load-tiles.cuh` 的 dp4a 分支（第 800–818 行）：

```cpp
const int scales8 = unpack_scales_q45_K(scales, ksc);
x_sc[i*(MMQ_TILE_NE_K/8) + i/8 + ksc] = scales8;   // 已是解包后的字节
```

所以内层拿到的 `sc` / `m` 指针指向的是**已经展开的字节数组**，不存在每次解包。

### P1''. 内层真正剩下的开销：4-bit 半字节提取

`vecdotq.cuh:533` 的 q4_K 实现：

```cpp
for (int i = 0; i < 4; ++i) {
    int sumi_d = 0;
    for (int j = 0; j < 2; ++j)
        sumi_d = dp4a((v[j] >> (4*i)) & 0x0F0F0F0F, u[i*2 + j], sumi_d);   // 每条 dp4a 配 shift+and
    sumf_d += ds8f.x * (sc[i] * sumi_d);
    sumf_m += ds8f.y *   m[i];
}
```

每条 dp4a 前面有一次 `>> (4*i)` 和一次 `& 0x0F0F0F0F`。

**可做的改法**：在加载阶段就把半字节拆成两个 int8 数组（MMA 路径本来就是这么做的

```cpp
x_qs[...] = (qs0 >> 0) & 0x0F0F0F0F;
x_qs[...] = (qs0 >> 4) & 0x0F0F0F0F;
```
），内层就只剩纯 dp4a。

**但这个改动会把 qs 区域的 SRAM 翻倍**：I=128 时从 16.9 KB 涨到约 33.8 KB，
整个 tile 逼近 40 KB → **occupancy 从 2 掉到 1**，收益大概率被抵消。

### 结论：GEMM 内核这条线到此为止

三次尝试的分析都被源码否证了（scale 外提 → 寄存器不够；6-bit 解包 → 早已预展开；
半字节拆分 → SRAM 翻倍）。**剩下能动的只有一个需要重新设计 SRAM 布局的大改，
且成功概率不高。**

Q4_0 能到 87% 而 q4_K 只有 61%，这个差距的根源是**格式本身**（Q4_0 每 32 值只有一个
fp16 scale，q4_K 有 8 个子块），不是内核写得不好。要抹平它只能换格式（P3）。

### P2.（已排除）激活只量化一次 —— 模型已经这样做了

查了 GGUF 的元数据：`minimax_h3: ffn=14336`，而 `mlp.fc1.weight` 的形状是 `[5376, 28672]`
= **2 × 14336**。也就是说 gate 和 up 已经是**一次融合的 mul_mat**（输出 28672），
后面接 GLU 拆开。激活确实只量化一次。

**P2 不存在，无需改动。**

### P3. 大 K 下的尾块合并（预期 +3~5%）

K=5376 = 21 × 256，K=28672 = 112 × 256，都除得尽，所以**当前形状没有尾块问题**。
但如果换分辨率/模型，K 不是 256 的倍数时，尾块会走 scalar 路径。
建议在 `mmq.cuh` 里检查 `k % MMQ_ITER_K` 的处理，对非整除情况加一个合并分支。

### P4. 用 `v_dot2_f32_f16` 替代 dp4a（不确定，需要实验）

RDNA2 有 `v_dot2c_f32_f16`（两路 fp16 乘加进 fp32），我在注意力内核里用过。
如果先把 q4_K 解包成 **fp16 对**（而不是 int8），就能用这条路径：
- 好处：省掉 int8 的 `scale/min` 整数运算（fp16 直接带 scale 做乘加）
- 坏处：fp16 精度比 int8 累加差，且解包多一步 int8→fp16 转换

**没有实测，只是可能性**。注意力内核的经验是 dot2 比 float2 快约 16%，
但那里输入本来就是 fp16。

## 四、不该再动的

| 手段 | 结论 | 证据 |
|---|---|---|
| J tile（8→128） | **已做完**，128 是编译期上限 | `static_assert(J <= 128)` |
| I tile（128→64） | 更差 | 22.96 vs 27.92 |
| occupancy（2→1） | 无差别 | 27.88 vs 27.92 |
| stream-K | +23% | 早前实测 |
| FORCE_MMQ | +45% | 早前实测 |
| 预解包成 int8 常驻 | 显存 11→19.5 GB，16 GB 卡装不下 | 算术 |

## 五、结论

**这张卡上 q4_K GEMM 的现实天花板**：
- 现在 61%，靠 P1（scale 外提）理论可达 **70% 左右**
- 要再往上就只剩「换 q4_0 这种简单格式」（87%）或换硬件

**建议顺序**：P2（半天，+2~5%，不改内核）→ P1（1–2 天，+10~15%，有 spill 风险）→ 其余不动。

如果目标是端到端：P1 拿到 15% 的 GEMM 提升，折算到采样循环约 **+8~10%**，
是这条线上最后一个两位数的机会。
