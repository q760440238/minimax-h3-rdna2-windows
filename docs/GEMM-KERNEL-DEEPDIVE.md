# GEMM 底层内核还能优化什么

日期：2026-11-02
全部基于本会话实测（RX 6900 XT / gfx1030，峰值 46.08 TFLOPS）。

---

## 一、先看一条关键曲线：解包复杂度决定上限

同一形状（5376×28672×2835）、同一个 MMQ 内核、同一块卡，**只换量化格式**：

| 格式 | TFLOPS | 占峰值 | 每 32 值需要做什么 |
|---|---:|---:|---|
| **Q4_0**（J=128） | **40.27** | **87%** | 1 个 fp16 scale，4-bit → int8 |
| Q4_1（J=128） | 37.24 | 81% | 1 个 scale + 1 个 min |
| Q8_0 | 32.27 | 70% | 纯 int8，无解包 |
| Q4_K（J=128） | 27.92 | 61% | **8 个子块，各带 6-bit scale + 6-bit min** |
| Q6_K（J=128） | 24.46 | 53% | 16 个子块 + 6-bit 高位重排 |

**结论：这张卡的瓶颈不是 LDS、不是 occupancy、不是 tile 形状——是解包。**

Q4_0 能跑到 87%，说明内存、dp4a 流水、网格调度全都没问题。
Q4_K 掉到 61%，差的 26 个百分点全是「每个 32 元素子块要单独取 scale/min 并应用」的开销。

这也解释了为什么之前所有的 tile 调参（J、I、occupancy、stream-K）最多只有 ±10%：
**它们动的是搬运，而瓶颈在算术。**

## 二、q4_K 的解包为什么贵（源码级）

`mmq-load-tiles.cuh` + `mmq-vec-dot.cuh` 里，q4_K 每个 256 值超级块：

1. `K_SCALE_SIZE = 12` 字节里打包了 8 个 6-bit scale 和 8 个 6-bit min
2. 取一个子块的 scale 要：移位 + 掩码 + 合并（两个字节拼 6 bit）+ 转 half
3. 4-bit → int8 展开：每 4 字节两条 `shift` + 两条 `and`
4. 内层 dp4a 之后，**每个子块还要一次 `scale * acc` 和 `acc += min * sum`**

对比 q4_0：只有**一个** fp16 scale，直接 `d * dot(int8)`，没有 min、没有子块。

## 三、可以动的四个点（按预期收益排序）

### P1. 把 scale 的应用从内层搬到外层（预期 +10~15%）

现在（概念上）：

```
for each 32-value sub-block:
    acc += scale_sub * dot4(q_sub, a_sub)
    acc += min_sub   * sum_a_sub
```

改成用 **8 个独立累加器**（每个子块一个），在 K 循环里只做纯 dp4a：

```
int acc8[8];                       // 一个 256-值超级块对应 8 个子块
for each sub-block s:  acc8[s] += dot4(q_s, a_s)     // 纯 dp4a，无浮点
// 超级块结束（K/256 次）才做：
total += Σ_s (scale_s * acc8[s] + min_s * sum_a_s)
```

代价：多 8 个整数寄存器（I=128/J=128 时寄存器已经很紧，**可能反而 spill**）。
收益：内层循环减少 2 次浮点乘加/子块 → 换算下来约 10–15%。

**这是最值得先试的一条**，但必须先量寄存器压力。若 I 或 J 要降一档来腾寄存器，
就可能互相抵消——这正是为什么要在独立微基准里做（`kernels/gemm_bench.cpp` 已经就位）。

### P2. 激活侧只量化一次（预期 +2~5%，且不需要改内核）

FFN 是 `fc1`（gate 和 up 两个输出）→ GLU → `fc2`。
现在 gate 和 up 是**两次独立的 mul_mat**，各自把同一份 F32 激活量化成 Q8_1 一遍。

把两个 mul_mat 合成一次「更宽」的（输出维度翻倍，共享同一份量化后的激活）
就省掉一半的激活量化开销和一半的激活读取带宽。

**这条要改 sd.cpp（FFN 构建方式），不是改内核，成本约半天，风险低。**

### P3. 大 K 下的尾块合并（预期 +3~5%）

K=5376 = 21 × 256，K=28672 = 112 × 256，都除得尽，所以**当前形状没有尾块问题**。
但如果换分辨率/模型，K 不是 256 的倍数时，尾块会走 scalar 路径。
建议在 `mmq.cuh` 里检查 `k % MMQ_ITER_K` 的处理，对非整除情况加一个合并分支。

### P4. 用 `v_dot2_f32_f16` 替代 dp4a（不确定，需要实验）

RDNA2 有 `v_dot2c_f32_f16`（两路 fp16 乘加进 fp32），我在注意力内核里用过。
如果先把 q4_K 解包成 **fp16 对**（而不是 int8），就能用这条路径：
- 好处：省掉 int8 的 `scale/min` 整数运算（fp16 直接带 scale 做乘加）
- 坏处：fp16 精度比 int8 累加差，且解包多一步 int8→fp16 转换

**没有实测，只是可能性**。注意力内核的经验是 dot2 比 float2 快约 16%，
但那里输入本来就是 fp16。

## 四、不该再动的

| 手段 | 结论 | 证据 |
|---|---|---|
| J tile（8→128） | **已做完**，128 是编译期上限 | `static_assert(J <= 128)` |
| I tile（128→64） | 更差 | 22.96 vs 27.92 |
| occupancy（2→1） | 无差别 | 27.88 vs 27.92 |
| stream-K | +23% | 早前实测 |
| FORCE_MMQ | +45% | 早前实测 |
| 预解包成 int8 常驻 | 显存 11→19.5 GB，16 GB 卡装不下 | 算术 |

---

## 五、结论

**这张卡上 q4_K GEMM 的现实天花板**：
- 现在 61%，靠 P1（scale 外提）理论可达 **70% 左右**
- 要再往上就只剩「换 q4_0 这种简单格式」（87%）或换硬件

**建议顺序**：P2（半天，+2~5%，不改内核）→ P1（1–2 天，+10~15%，有 spill 风险）→ 其余不动。

如果目标是端到端：P1 拿到 15% 的 GEMM 提升，折算到采样循环约 **+8~10%**，
是这条线上最后一个两位数的机会。
