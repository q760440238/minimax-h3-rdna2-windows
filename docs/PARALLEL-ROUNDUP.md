# 并行优化实验汇总（2026-11-02）

四条线并行执行的结果。**其中一条是明确否定**，两条有增量，一条是分析。

## 1. VAE / 加载剖析（✅ 完成，findings 最多）

非采样时间**恒定占 23%**：

| | 22 帧 | 56 帧 |
|---|---:|---:|
| 总计 | 64.77 s | 180.07 s |
| 采样 | 49.90 s（77%） | 138.42 s（77%） |
| **视频 VAE 解码** | **7.95 s（12.3%）** | **24.24 s（13.5%）** |
| 扩散权重 staging | 4.79 s | **11.13 s** |
| 视频 VAE staging | 2.06 s | 2.08 s |
| 音频 VAE | 1.06 s | 1.37 s |

### 两个新发现

**A. 56 帧的 VAE 解码分成三次**（9.26 + 6.93 + 6.92 = 23.11 s），22 帧只有一次（7.90 s）。
每次 ~7–9 s，56 帧 = 3 次。

**B. 56 帧的权重 staging 被拆成 51 块**（每块 206.72 MB × 0.21 s = 11.13 s），
而 22 帧是一次性 10.98 GB（4.79 s）。原因：56 帧启用了 `--max-vram 11`，逼着分批装入。

### 缓解措施实测

| 措施 | 结果 |
|---|---|
| `--vae-tiling` 在 22 帧 | **+15.5 s（4/4 次一致变慢）**，比 gen.ps1 注释里写的「+2%」严重得多 |
| `--vae-tile-size 256x256` | 最慢的解码（15.16 s）；512 左右反而接近基线 |
| 省略 `--audio-vae` | **可用**（exit 0、无错误、有画面无音轨），只省 0.8–1.1 s |
| `--vae-on-cpu` | **不可用**（视频解码 >5 分钟 vs 8 秒）|

### ⚠️ 测量陷阱（重要）

**页缓存状态会让 `--mmap` 的采样时间差 35%**：冷缓存 67.4 s vs 热缓存 49.9 s（22 帧）。
本轮有两次测量因此报废。**任何 A/B 必须先跑一次热身**。

## 2. 注意力内核接入（❌ 明确否定）

**结论：我自写的注意力内核比 ggml 的 flash-attention 慢 22%。**

| 56 帧 / 8 步 | 采样 |
|---|---:|
| 默认（ggml FA） | 366.22 s |
| `SD_ATTN_V2=1`（我的内核） | **447.76 s（+22.3%）** |

独立微基准里它是 8.76 TFLOPS，但接进链路反而更慢，原因有三：

1. **q/k/v 是 F32**（微基准是 F16），带宽翻倍
2. **v 是融合 qkv 缓冲的跨步视图**，必须先 `ggml_ext_cont` 物化——每层 200 MB 拷贝 × 50 层
3. ggml 的 FA 内核本身调得不错

有价值的副产品是**诊断**：之前「只在 H=4/L=1024 上触发」的真因是**启动时的 FA 自动探针图**，
不是模型注意力；模型主注意力（H=56, L=2970@22f / 7132@56f）是被「v 非连续」和
「FA 分支先执行」两道门挡住的。

**处置：保持 opt-in（`SD_ATTN_V2=1`），不默认开启，不删除。** 默认路径不产生任何额外图节点。

## 教训：并行跑 GPU 基准是错的

这轮我用三个子代理并行，但**它们共享一块 GPU**。结果：

- 注意力 A/B 的第一对数据被 GEMM 扫描污染成 366/448 s（正常应该是 ~139 s）
- GEMM 扫描中途的数字全部作废（q4_k 从 25.4 掉到 6.9 TFLOPS）
- 我自己后来的一次 56 帧跑到 445 s/步，也是残留进程导致

**正确做法：GPU 基准必须串行，只有「写代码 + 编译」可以并行。**
下一次要把并行度用在「一个跑 GPU，其余改代码/写文档」这种组合上。
